# bituah — локальный парсинг страховых полисов на иврите (Swift)

Утилита и библиотека на Swift, которая принимает PDF страхового полиса на иврите и **полностью офлайн**
(без единого сетевого вызова) извлекает восемь целевых полей в JSON. Тот же код — библиотека `BituahCore` —
без изменений собирается под iOS 16+; CLI и SwiftUI-демо здесь нужны для проверки.

```
insured_id · company_name · policy_number · insurance_type · start_date · end_date · monthly_premium_ils · deductible_ils
```

## Запуск в одну команду

```bash
./run.sh
```

Собирает release, парсит `Samples/*.pdf` → `result.json` (+ `result.details.json` с confidence и evidence по каждому полю),
генерирует «тяжёлые» варианты тестовых документов и печатает отчёт о точности (`metrics.json`).

Требования: Xcode 15+ (Swift 5.9). Внешних Swift-зависимостей нет. Для **сканов** (PDF без текстового слоя)
нужен Tesseract с ивритской моделью — `brew install tesseract tesseract-lang`; для цифровых PDF он не нужен.

Другие команды:

```bash
swift run bituah parse policy.pdf                 # один документ → JSON в stdout
swift run bituah parse Samples -o result.json     # папка → result.json + result.details.json
swift run bituah text policy.pdf [--force-ocr]    # отладка: нормализованные строки, которые видит экстрактор
swift run bituah eval                             # таблицы точности по ground_truth.json
swift run BituahDemo                              # SwiftUI-демо для macOS (RTL-форма, confidence и evidence по полю)
swift test                                        # 28 unit/golden тестов
./run-device.sh                                   # iOS-приложение (iOSApp/) — сборка, подпись и установка на подключённый iPhone
```

iOS-приложение (`iOSApp/`, генерируется `xcodegen` из `project.yml`) подключает `BituahCore` как локальный
пакет, содержит три тестовых полиса и открывает любой PDF из «Файлов». На iPhone работает уровень текстового
слоя (Tesseract в демо не линкуется); поля показываются с confidence и evidence-строкой, интерфейс RTL.
Для установки на устройство нужен Xcode с вашим Apple ID (команда в `project.yml`, поле `DEVELOPMENT_TEAM`).

## Результат на тестовых документах

`result.json` совпадает с `ground_truth.json` по всем 24 полям трёх присланных PDF. Полный отчёт — ниже, в разделе «Измерение».

## 1. Архитектура и почему именно она для мобильного устройства

```
PDF ──► PDFKit text layer ──(есть текст?)──► нормализация иврита ──► экстрактор полей ──► JSON + confidence
            │ нет                                   ▲
            ▼                                       │
        растр 300 dpi ──► Tesseract heb ──┐         │
                    └──► Vision (цифры) ──┴─ геометрическое слияние (OCRFusion)
```

**Уровень 1 — родной текстовый слой (PDFKit).** Подавляющее большинство полисов израильских страховщиков и
отчёты «Хар Битуах» — цифровые PDF, а не сканы. PDFKit достаёт текст со строчными bbox за миллисекунды,
без модели и без батареи; на iOS это тот же фреймворк. На трёх тестовых документах весь путь занимает **36–81 мс**.

**Уровень 2 — OCR только для страниц без текста.** Apple Vision — очевидный кандидат для on-device OCR, но
**иврита в нём нет**: `VNRecognizeTextRequest.supportedRecognitionLanguages()` на macOS 27 / iOS 27 отдаёт
арабский, но не `he` (проверяется `swift run bituah info`). Поэтому ивритские слова читает **Tesseract 5 `heb`**
(здесь — бинарник Homebrew через `Process`; на iOS — тот же libtesseract + leptonica как xcframework за тем же
протоколом `OCREngine`, код пайплайна не меняется). Модель `heb.traineddata` — ~1 МБ (tessdata_fast), CPU, ~2–4 с на страницу
A4 при 300 dpi на M-серии; на iPhone ожидаю 3–6 с, что для «сфотографировал полис» приемлемо.

**Слияние Tesseract + Vision по геометрии (`OCRFusion`).** Замер показал, что Tesseract-heb уверенно читает
ивритские подписи, но теряет тонкие/светлые цифры в ячейках значений (`245.50 ש"ח` → `0 ש"ח`), а Vision без
иврита читает **все** цифры, даты и номер полиса без единой ошибки. Каждый числовой токен Vision заменяет то,
что Tesseract прочитал на той же строке в том же месте (по пересечению bbox), строка пересобирается справа-налево.
Цена — один дополнительный проход Vision (~0.4 с). Эффект на сканах: **19/24 → 24/24**.

**Нормализация иврита (`HebrewNormalizer`).** Unicode-шум (гершаим `״` vs `"`, макаф, NBSP, никуд, bidi-метки);
три гипотезы восстановления логического порядка для строк, сохранённых в визуальном порядке (`הסילופ רפסמ`),
выбираемые по словарю страховой лексики с биграммами; и **документный** детектор инверсии цифр (см. раздел 3).

**Экстрактор полей — детерминированные правила, а не LLM.** Для каждого поля: якорные ключевые слова с весами
(`מספר תעודת זהות` > `ת.ז` > `תז`), кандидаты в той же строке после метки и в 1–2 следующих строках (в израильских
таблицах метка и значение часто на соседних строках), скоринг «вес метки − расстояние по строкам + валидация»
(checksum ת.ז, валидность даты, наличие `ש"ח`), затем canonical-форма. На выходе — значение, **confidence** и
**evidence** (строка документа, из которой оно взято) — это то, что пользователь видит в UI и что позволяет
собирать разметку в проде.

Почему не VLM/LLM как основной движок на телефоне:

| | правила + Tesseract/Vision | локальная VLM (Qwen2-VL-2B q4) |
|---|---|---|
| размер на устройстве | ~1 МБ (heb.traineddata) | 1.5–4 ГБ |
| время на страницу | 0.04 с (текст) / 3–5 с (скан) | 10–30 с, троттлинг |
| объяснимость | evidence-строка на каждое поле | нет |
| детерминизм / тестируемость | полная | нет |
| галлюцинации цифр | невозможны | реальный риск для ת.ז и сумм |

Где локальная модель **нужна** — это следующий шаг, а не замена (см. план в разделе 3): fallback для полей с
confidence ниже порога и для нестандартных бланков, плюс LLM-as-judge в цикле разметки.

## 2. Чем и как измеряли точность

**Ground truth.** `ground_truth.json` из задания (3 документа × 8 полей). К нему `bituah make-testset` строит
два «тяжёлых» варианта каждого документа с тем же ground truth:

* `scan_*` — растр 200 dpi, поворот 0.6°, размытие, шум, ч/б, обёрнут в PDF **без текстового слоя** → проверяет
  OCR-уровень целиком;
* `visual_*` — страница перенабрана так, что текстовый слой хранится в визуальном порядке (LTR-override).
  Выяснилось, что PDFKit при извлечении сам прогоняет bidi, и на выходе получается логический иврит с
  **зеркальными цифрами** (`810294830`, `6202/10/10`, `05.542`) — ровно та «инверсия цифр», которая встречается
  в реальных израильских PDF. Вариант проверяет документный детектор инверсии.

**Метрики.**

* *Совпадение полей* — точное после нормализации строк (гершаим/кавычки/пробелы); числа с допуском 0.005;
  даты в ISO. Считает `Metrics.score`, печатает `bituah eval`.
* *CER / WER* — расстояние Левенштейна между текстом OCR и **родным текстовым слоем того же документа**
  (символы / слова), после одинаковой нормализации обеих сторон.
* *Латентность* — по стадиям (`text_layer`, `ocr_primary`, `ocr_digits`, `normalize`, `extract`) в `result.details.json`.
* *Unit/golden тесты* — 28 тестов (`swift test`): checksum ת.ז, парсеры дат/сумм, нормализатор (три гипотезы
  порядка, инверсия цифр, склейка ячеек строки), экстрактор на рукописных строках (inline-метки, годовая премия → /12,
  «אין» → 0, процентная франшиза → null, `חיסכון פנסיוני` в полисе жизни не перебивает `חיים`), golden-тесты на
  трёх PDF и их вариантах.

**Результаты** (`./run.sh`, Apple Silicon, release):

| набор | insured_id | company | policy_no | type | start | end | premium | deductible | итого |
|---|---|---|---|---|---|---|---|---|---|
| цифровые PDF (text layer) | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **24/24** |
| visual-order → инверсия цифр | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **24/24** |
| сканы, Tesseract heb + Vision | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **24/24** |

OCR-качество на сканах (`heb+eng`, psm 4, 300 dpi):

| файл | CER | WER | OCR, с |
|---|---|---|---|
| scan_test_policy_1_harel_health.pdf | 15.7% | 18.0% | 3.7 |
| scan_test_policy_2_migdal_auto.pdf | 15.3% | 24.6% | 2.0 |
| scan_test_policy_3_phoenix_life.pdf | 12.2% | 22.5% | 1.6 |
| **среднее** | **14.4%** | **21.7%** | |

CER ~14% при 24/24 по полям — нормальная картина: ошибки OCR сосредоточены в колонтитулах, латинице и длинных
примечаниях, а поля защищены якорями, валидацией и слиянием с Vision.

Абляции на сканах (`bituah eval --psm N [--no-cross-check] [--dpi N]`):

| конфигурация | поля | CER |
|---|---|---|
| psm 4 + Vision-слияние (по умолчанию) | 24/24 | 14.4% |
| psm 4, без Vision | 19/24 | 14.8% |
| psm 3 + Vision | 24/24 | 14.5% |
| psm 6 + Vision | 22/24 | 19.0% |
| psm 6, без Vision | 7/24 | 27.2% |
| psm 4 + Vision, 200 dpi | 24/24 (в 2× быстрее) | 12.7% |

Без Vision пропадают именно суммы и номер полиса; без слияния и с неверной сегментацией (psm 6) результат
разваливается до 7/24 — то есть **точность держится на слиянии и валидации, а не на одном OCR**.

**Честные оговорки.** Набор — три синтетических документа одного шаблона (HTML→PDF). Все три ת.ז в ground
truth **не проходят** контрольную сумму, поэтому checksum в скоринге — только бонус, не фильтр. Оценка на
реальных полисах разных страховщиков (разные шаблоны, многостраничные, таблицы покрытий, отчёты «Хар Битуах»)
— первое, что нужно сделать, и для неё нужен размеченный вручную набор (см. ниже).

## 3. Что не закрыто по ивриту и как решать на iOS в проде

**RTL / визуальный порядок текстового слоя.**
Сделано: три гипотезы восстановления (полный реверс с сохранением LTR-ранов, пословный реверс, обратный
порядок слов) со словарным скорингом; склейка ячеек одной визуальной строки справа-налево по bbox.
Не закрыто: смешанные строки, где реверснута только часть ранов; шрифты без ToUnicode (текст извлекается как
мусор). План: работать на уровне глифов — брать позиции символов из PDFKit (`characterBounds`) и восстанавливать
порядок чтения по координатам, а не по строке; для битых ToUnicode — падать в OCR по этой странице.

**Инверсия цифр.**
Сделано: документный детектор — если зеркальное чтение чисел «правильнее» литерального (даты становятся
валидными, разряды `1,500` — корректными) чаще, чем наоборот, все цифровые раны документа зеркалятся.
Важное наблюдение: **контрольная сумма ת.ז симметрична относительно реверса** (веса 1,2,1,2,… палиндромны),
поэтому она *не может* обнаружить инверсию 9-значного номера — детекция должна опираться на даты и суммы,
что и сделано. Не закрыто: документ, где инвертирована только одна строка. План: детектор на уровне строки
с bbox-эвристикой направления рана (цифры, нарисованные справа-налево, имеют убывающие x-координаты глифов).

**Сложная вёрстка таблиц.**
Сделано: склейка фрагментов одной строки, поиск значения в 1–2 следующих строках. Не закрыто: многоколоночные
таблицы покрытий (несколько сумм/франшиз на разные риски в одной таблице), заголовки таблиц, многостраничность,
отчёты «Хар Битуах» с десятками полисов на человека. План: (a) детекция линий и ячеек по растру (OpenCV-подобная
морфология на CoreImage / vImage) → таблица ячеек с координатами; (b) экстрактор по ячейкам «строка × колонка»;
(c) маленькая layout-модель (LayoutLM-класс, ≤50 МБ, CoreML) для разметки блоков, обученная на нашей разметке.

**OCR иврита на устройстве.**
Сейчас Tesseract `heb` (LSTM 2017 г.): CER 12–16% на «грязных» сканах, слабость к тонким цифрам. План:
1) Tesseract как xcframework + Vision для цифр — как здесь, это уже даёт рабочий MVP;
2) дообучить распознаватель строк (PARSeq / TrOCR-small, или дообучение `heb.traineddata` на синтетике из
   шрифтов израильских бланков + реальные строки) → экспорт в CoreML, int8; детекцию строк оставить Vision
   (`VNDetectTextRectanglesRequest` язык-независим); цель — CER < 3% на строках полей;
3) замер на устройстве: CER/WER, точность полей, p50/p95 латентности, пиковая память на iPhone 12/15.

**Локальная модель как fallback (квантизация, LoRA).**
Правила покрывают типовые бланки; для нестандартных нужен on-device LLM, который получает нормализованные строки
(не картинку) и возвращает JSON по схеме: Qwen2.5-1.5B / Gemma-2-2B в 4-bit (MLX-Swift или llama.cpp), LoRA
на синтетических + размеченных полисах, constrained decoding по JSON-схеме, вызов **только** для полей с
confidence < 0.6 или при провале валидации. Оценка — тот же `eval`: точность по полям, латентность, память,
и обязательное сравнение с правилами на одном наборе. Пока модель не обгонит правила на реальном наборе — она
не включается.

**Данные и процесс.** Набор из ≥200 реальных полисов от 6–8 страховщиков, размеченный вручную (двойная разметка
спорных полей), с версионированием ground truth; `eval` в CI на каждый PR; в приложении — evidence и confidence
на каждое поле, чтобы пользовательские исправления возвращались в разметку. Никакие данные клиента не покидают
устройство: сетевых вызовов в коде нет, что легко проверить — `grep -r URLSession Sources` пуст.

## Структура

```
Sources/BituahCore/            библиотека (iOS 16+ / macOS 14+), без зависимостей
  Text/     PDFTextLayerExtractor, HebrewNormalizer, Pattern (обёртка над NSRegularExpression)
  OCR/      OCREngine (протокол), TesseractCLIEngine, VisionOCREngine, OCRFusion, PageRasterizer
  Extract/  FieldExtractors, IsraeliID, DateParser, AmountParser, Insurers (лексиконы)
  Pipeline/ PolicyParser — PDF → строки → нормализация → поля
  Eval/     Metrics (совпадение полей, CER/WER), TestSetGenerator (scan_* / visual_* варианты)
  Models/   PolicyFields, ExtractionResult, JSONValue (упорядоченный JSON, числа в стиле 1500.0)
Sources/bituah/                CLI: parse · text · make-testset · eval · info
Sources/BituahDemo/            SwiftUI-демо для macOS (RTL, confidence/evidence по полю, drag&drop PDF)
iOSApp/                        iOS-приложение (xcodegen project.yml + SwiftUI), ./run-device.sh ставит на iPhone
Tests/BituahCoreTests/         unit + golden тесты
Samples/                       тестовые PDF из задания; Samples/variants — сгенерированные варианты
ground_truth.json · result.json · result.details.json · metrics.json
```
